## 怎样证明属于这段视频

程序读取[视频锚点](../data/video-anchors.json)，以球员、节次和画面覆盖的比赛时钟范围产生投篮候选，再逐项核对：

1. 比赛 ID 在比赛页、逐回合、逐次投篮中一致；官方球队和本场名单中的号码与已查看画面相符。
2. `isFieldGoal=1`，球员、球队、节次、命中结果、两分类型均一致。`actionNumber` 在投篮行中须唯一；不能把同号码的封盖记录也当成投篮。
3. 官方候选事件的记分结果与视频后比分相同；前一个明确记分状态与视频前比分相同；只允许出手方按本次投篮结果增加应有的分数。
4. 以 `actionNumber` 关联 `eventId`，核对逐次数据的比赛、球员、节次、命中和两分类型；概率值必须存在、有限且在 0–1 范围。
5. 只有一个完全一致的候选才返回 `verified=true`。缺字段、概率无效、比分矛盾、错误关联键、重复事件或多个通过候选均不能通过。

[可执行匹配函数](../data/match_events.py) 无网络和第三方依赖；[机器匹配证据](../data/event-bindings.json) 保存每项检查、原始对应行及结果。保存的 `verified` 表示**本队针对已标注练习素材的来源一致性核查通过**，不是 NBA 官方对我们产品的认证。

这不是自动视频理解或时钟识别：锚点由 AI 助手实际查看本地抽帧后编辑记录；尚无人类篮球专家签字复核。程序验证这些输入的内部一致性，不能证明任意新视频与输入锚点相符。换视频时必须重做锚点并核对源视频哈希。

画面时钟用于覆盖事件的区间约束，不作逐帧时间真值。阿门片尾近景、弗拉格开头近景，以及平移缩放造成的坐标变化仍存在；当前数据不支持逐帧跑动轨迹。

## 给产品的事实边界

[stories.json](../data/stories.json) 提供两个案例，每例四段已核查的编辑候选、三种观看视角和可点击证据。`hook.choices` 的 `player / defender / data` 与 `storyOptions` 同 ID，各有独立文案和回看位置；这是选焦点，不是有唯一正确答案的测验。Agent 可按视角选取与重组内容，不能把静态候选伪称为模型刚刚发现的新事实。

`shotMetric.rawValue`、对应 `evidence.value`、`officialEvent.expectedFg` 使用相同的原始概率；三个对象的比赛、事件、球员 ID 一致。概率只从已验证工具输出注入显示，不允许模型改数。页面及成片应明确名称为“预期投篮命中率”。依[官网术语页](https://china.nba.cn/inside-the-game/glossary)和此前官网脚本核查，它表示此次机会的概率型参考，不是该球员个人保证命中的概率，也不是比赛胜率。

51.0% 和 44.5% 都不应被包装成“超低概率神球”。安全故事是：弗拉格的终结发生时仍可看见防守举手；阿门一球可以清楚回看持球转移和起跳顺序。官方确认阿门这次记杜兰特助攻，但这不等于可以把全部得分功劳或反事实增益归给助攻者。

`locX / locY / side` 原样保留在 `officialEvent.shotLocation`，只代表官网出手点位。没有将它们冒充视频像素或贴到球员脚下。没有取得本事件的 Gravity、防守压力、Leverage 或 Win Probability，未知值不补零。

另一个来源陷阱：gpShot 的 `matchup` 字符串呈现的主客队方向与 NBA.com 比赛元数据不一致。本产品采用比赛页的 `homeTeamId / awayTeamId`，不用该字符串推断主客场。日期同时保存北京时间日期和当地比赛日期，避免把素材名中的次日误认成另一场。

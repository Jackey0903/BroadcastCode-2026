三条调用链：

1. 浏览器原生 `video` 解码/播放：保持原样。
2. `requestVideoFrameCallback → frame → checkClipEnd / syncContent`：两种模式都运行，战术时间和业务刷新不受材质开关影响。
3. `frame → paintAmbience → paintAmbienceSource → liquidGL 动态合成/上传`：默认路径在 `paintAmbience` 即返回；液态专属 ResizeObserver 也在回退时断开。没有删除业务帧回调。

## 3. 关闭液态玻璃的证据

- 默认初次加载实际拦截 Canvas `getContext`，GPU context 创建尝试为0；实际 Renderer/Lens/Canvas 均0。
- 默认没有注册液态动态背景，没有氛围源尺寸监听；Canvas `drawImage(video)` 计数为0。
- 从 CSS 显式启用 liquidGL，确认2个实际渲染器；切回后，两个旧渲染器 `_destroyed=true`、`backend=null`、Canvas 断开、清理数组和动态节点清零。
- 切回后继续播放并将窗口改为1440×810：渲染调用0、视频 Canvas 绘制0，`ambience.observerActive=false`；原视频时间与战术显示时间同时前进至1.189011秒，原配置完全一致。
- 实际非 BFCache 离页后，两个旧渲染器及其监听器销毁，全局活动渲染器不存在，氛围监听断开；随后验收浏览器已关闭。BFCache 的冻结/恢复不是本次离页测量对象。

见[生命周期与功能原始记录](../dev/evidence/stability-20261010/regression.json)。诊断始终可通过 `window.broadcastDiagnostics()` 查看，调参界面也保留实际模式详情。

## 5. 剩余风险

- **“CSS 稳态丢帧明显优于 v5”未被本轮证明**：三个方案均已接近本机刷新上限；不能把消除工作量直接写成已测得帧率提升。
- 全片多次切换仍有7/1287丢帧，自动展开最长单次帧等待41.6ms。相较本次液态283ms长等待明显缩短，但不保证所有系统负载下零停顿。
- 只验收本机 Chrome；Safari、其他设备/窗口/DPR、正式部署环境的实际表现未测。1440×810只用于释放后重排检查，完整A/B/C固定1512×949、DPR1。

## 6. 最终结论

- **能否稳定演示：** 本机 Chrome 可以，已完整播放并保留三态、数据同步和中文调参；存在上述少量丢帧边界。
- **能否用于比赛提交：** 可以作为本地稳定提交候选；正式发布环境尚未验收，本轮仅授权提交和推送分支，部署仍需另行授权。此结论不是赛事验收或全设备性能保证。
- **liquidGL 是否可恢复：** 是，3.0.0和v5补丁未删未改、光学预设完整保留。通过“外观与组件→材质模式”或 `/?glass=liquid` 显式启用；不带参数的首次加载始终是CSS。

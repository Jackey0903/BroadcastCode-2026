# 评委视角独立评审：先让观众看懂一个回合

日期：2026-10-06。用途：支持 Team02 选题与开发优先级。本文件综合本地规则分析、9 月 28 日培训逐字稿，以及本轮主代理通过 Chrome 实际读取的最新《参赛终极指南》（页面显示 10 月 5 日 13:27 更新）。官方权重与本队内部验收标准分别标明；不保证名次。

## 1. 评委真正要验收的结果

最强的主线是：**把一个普通直播回合，变成观众能亲自探索、且每个结论有依据的战术回放。** 用少量准确的关键标注揭示机会是怎样产生的，让观众发现只看进球时忽略的贡献。

这直接对应两位培训讲者反复强调的目标：NBA 方希望数据帮助理解精彩之处，并明确反对堆积数据；AWS 方要求网页美感、操作性、准确度，同时检查实际部署及 Agent 能力。系统应同时提供“第一次打开就看懂”的自动讲解路径，以及“点一下就能验证”的交互证据路径。

最新指南已经明确：初赛自动评分 35 分看架构稳定性、AWS 有效使用、服务组合协同以及输入—处理—输出完整性。各服务精确分值未见公布，不能按服务个数自创公式。私有代码被读取，CloudFront/CDK/AWS Agent 为重点要求；只有声明没有实际功能的空架构缺少说服力。

初赛人工 55 分现已明确拆为 **数据/内容准确性 30 分（NBA 评委）+ UX/UI 体验 25 分（AWS SA）**。并列比较依次为人工分、机器分、准确性、UX/UI、问答。误认球员、箭头指错、把赛季统计说成此次出手值，直接威胁最大单项和重要并列排序项。技术复杂度本身也不等于观众体验。

决赛是独立的新评分，初赛分不带入：**技术方案与架构 18、实现深度与难度 18、数据运用准确性 15、讲解答辩 9、视觉作品效果 40**。视觉项包括可视化、篮球叙事感染力、质感和交互创新；实现深度关注数学/统计/算法、识别后二次加工、自定义指标，不能只调接口后展示。每队 5 分钟讲解加提问，约 10 位评委用同一评分表。主策略因此是：初赛用准确性与可靠体验进前八，决赛让这套可信分析转化成强视觉叙事，并拿出真正的数据加工算法。

最新指南还明确：数据只有出手瞬间点位，没有逐帧轨迹；范围排除实时接入、数字孪生、跑动轨迹复原、判罚与博彩。Agent 必须把数据叠加在真实比赛视频上，解说（AI 或人工）可选。提交包含 Agent、Private GitHub、说明、演示视频，以及 CloudFront 承载的考试完整作品成片；链接须在 20:00–22:20 有效。统一 Agent 接口、输入及产物路径须依 Quickstart 实现。

## 2. 四类方案的比较

以下是内部判断，不是对其他参赛队实际方案的观察。

|方向|最有价值的亮点|同质化与主要风险|建议定位|
|---|---|---|---|
|全场逐帧球员/球追踪|连续标注在其他场景可能有技术价值|本赛题明确没有逐帧轨迹，并排除跑动轨迹复原；同时存在遮挡、切镜、身份错误风险|排除主方案；只做必要的视频帧定位和标注对齐，不宣称或交付轨迹复原|
|篮球聊天机器人|交互自然，可回答观众疑问|自由聊天容易变成通用大模型套壳；评委还需自己想问题；未必有视频同步和数据依据|作为证据限定的附加入口：预设三条与当前回合相关的问题，回答可跳到相应画面|
|战术解释短片 + 回合互动回放|同时满足视频叠加、篮球解读、UI、操作性和可快速展示；适合短考试视频|若只有手工做好的动画，无法证明 Agent；若只有旁白，会和普通集锦雷同|推荐主产品：真实 Agent 生成事件与讲解脚本，输出自动播放和可探索两种观看方式|
|反事实模拟“换一种选择会怎样”|容易形成记忆点，能显示球商和交互深度|没有校准模型与真实状态时，胜率、命中率和因果判断容易伪精确；虚拟轨迹可能被当作真实记录|后置加分项，先做“教练选项板”：冻结决策时刻、比较可见传球/出手窗口，明确标注战术假设，不编量化收益|

推荐组合遵守题目边界：真实比赛视频是主舞台，输出完整增强成片，并在网页上提供时间跳转、原片对照和证据探索。它要形成一个强记忆点：**观众先看见结果，再看见创造结果的人和决定性一步，并能点击验证。** 若当前素材没有适合“隐藏贡献者”的证据，就选择另一条被画面和数据支持的故事，不能为了产品口号捏造战术。

## 3. 内部冲冠评审框架

下列五项均按 0–4 级做内部评审，**不是官方 55 分分解，也不与官方分数换算**。可以等权合计观察版本进步；任何硬门槛失败时先修复门槛。

|维度|0–1 级：不可交付或薄弱|2 级：可用|3–4 级：有竞争力|
|---|---|---|---|
|篮球解释与证据|球员、动作、时序或数据有关键错误；主要是泛泛旁白|能正确描述事件，并注明数据来源|解释关键选择和攻防反应；事实、官方指标、推断边界清楚；点击即可回到证据帧|
|观看收益|只是原视频加标签或堆数字|有清楚的回合梳理|普通观众能说出至少一个原先没注意到的战术贡献，专家也认可解释克制、准确|
|视觉与交互|标注错位、遮挡、信息过载、控制难找|能正常播放、暂停、跳转|默认路径无需讲解即可操作；关键时刻冻结/慢放、原片对照和证据展开相互配合|
|真实自动处理|结果手工硬编码且没有对应自动流程|新素材能自动形成事件和讲解|新输入可重复跑通，输出结构化、失败可定位、低置信可降级，修订历史可追踪|
|交付与技术说服力|CloudFront 访问失败、缺关键部署要求或无法核验代码|云端运行、CDK 和 Agent 实际参与|版本一致、运行记录清楚、服务各有业务用途，演示不依赖工程师临场抢救|

内部硬门槛建议：

1. 未知新素材至少演练一次完整输入到 CloudFront 可播放输出，记录总耗时。
2. 已发布结果中，不允许保留已知的球员误认、事件错配、伪造官方数值或切镜后仍显示的旧标注。无法确认时隐藏精确标签或降级到镜头级解释。
3. 官方数值都能追溯来源、对象和统计区间；模型判断不能标成官方结论。
4. 三项部署要求、私有仓库、Portal 提交状态与当前版本对应；运行前复核本队身份、区域及权限时效。
5. 由未参与开发的人从新浏览器打开页面，完成“观看 → 找关键时刻 → 查看解释 → 回到原片”，无需口头指导。

## 4. 应对实际评分的证据设计

自动评分读取代码，因此最终文档应让真实能力容易找到：README 给出主流程、模块入口、CDK 资源映射、Agent 调用入口、可复现命令与测试覆盖。使用服务必须对应实际功能，不能只列 Logo。

人工评审打开网页，因此首页应直接出现可播放的考试回合和一个清楚的问题，例如“这次空位，是哪一步创造的？”问题需要匹配素材。将复杂功能放在观看过程中自然出现，第一屏不展示空仪表盘、上传表单或十几个开关。

可以把每次发布的 manifest 与结构化事件、来源索引、模型调用记录关联，使技术评委核对真实流程。面向观众的页面只展示有助于理解或判断可信度的信息，不暴露云资源细节、凭证或内部调试输出。

## 6. 90 秒效果演示节奏

这是嵌入官方 5 分钟讲解的核心效果演示段落。建议其余 210 秒分给真实分析算法与证据 90 秒、架构和运行验证 60 秒、局限与价值收束 60 秒；根据正式提问安排演练节奏。若临场需要压缩到 60 秒，优先保留实际回放与关键证据。

|时间|观众看到什么|讲什么|
|---|---|---|
|0–10 秒|正常速度播放回合的关键结尾|提出一个篮球问题，不先介绍技术栈|
|10–30 秒|点击“看懂这一球”，进入自动导演的三段解释|展示起因 → 防守反应 → 决策/终结；每幕只一个重点|
|30–55 秒|在决定性时刻暂停，切原片对照，展开一条官方数据或证据|解释何人创造了空间、为何这次选择合理，严格匹配实际素材|
|55–70 秒|评委点击另一关键时刻或预设问题，页面跳回对应画面|证明这是可探索的产品；让操作本身说明价值|
|70–80 秒|极简流程或结果记录，显示输入素材、生成时间和可追溯输出|一句话说明 Agent 自动完成什么，什么来自官方数据|
|80–90 秒|返回最有说服力的画面，原片与增强回放对照|用观众新理解的一件事收束；避免声称已经解决全场分析|

同一轮讲解的技术部分应备：输入和输出契约、模型与规则各做什么、低置信如何处理、真实 AWS 调用、从新素材到发布的实测耗时。讲解主线持续围绕“观众多理解了什么”。

## 7. 为决赛 18 分实现深度提供可信证据

不需要凭空发明一个看似精确的“篮球 IQ 分数”。推荐把真正的工程难点做成可检验的二次加工链：**镜头边界 → 时间候选 → 时序一致性 → 官方出手数据关联 → 可追溯的叠加与讲解脚本**。最终按训练素材难度选择其中能确实做好的环节。

|具体算法工作|超出直接调模型之处|怎么证明有效|不能声称什么|
|---|---|---|---|
|镜头切换检测与标注时段控制|区分连续镜头、切镜和回放；镜头改变时立即关闭不再适用的空间标注，依据出手瞬间点位显示对应解释|人工核对切镜时刻和出手帧，比较错误持续显示的帧数、出手时刻偏差；展示处理前后对照|不能扩展成赛题已排除的跑动轨迹复原，也不能把一个出手点延伸成运动轨迹|
|受约束的事件时间轴|模型输出多个传球/接球/出手候选；用事件顺序、时段边界和可见性约束筛选，保存拒绝理由|与人工核对的时间点比较事件定位误差和错误事件数，做“原始模型输出 vs 二次加工”对照|不能把规则自洽当成事实正确；仍需画面核验|
|官方数据与视频事件的匹配|依据球队、球员、节次、比赛时钟、动作类别等可得字段匹配；显式处理一对多、缺失和冲突|保留匹配键和证据，核对已知样本；无唯一匹配时拒绝贴上事件级数值|不能用“最接近的统计”冒充当前事件数据|
|信息排序与画面编排|从已验证事件中选转折、解释、结果；约束标注数量、屏幕碰撞和显示时段，输出确定性脚本|同一回合对照全量标签与受约束呈现，核查重叠、遮挡、阅读时长以及用户理解结果|不能仅凭审美规则宣称提高篮球预测准确率|

最低可信算法证据包：保留同一素材上的原始输出、加工后输出、人工核对基准、误差计算方法、可复现命令，以及失败例。训练片段很少时只报告这些片段的结果，不宣称泛化到整个 NBA。人工标注基准与允许的参赛结果校正是两件不同的事，后者仍须符合规则。

若使用自定义指标，名称必须明确属于本系统，并公开公式、单位、输入范围与局限。例如可以报告“标注覆盖了多少已核对关键事件”“标注时间与已核验事件的重合比例”，但这些是系统质量指标，不是官方篮球指标。由画面估算的距离如未校准只能用图像坐标或相对描述；只有验证过球场标定才能称为米。不建议首版预测某个反事实选择能增加多少胜率。

对决赛的解释可以很直接：大模型提供候选理解，本系统的时空加工与证据约束将它转换成可验证、可播放的篮球叙事。评委能够在一个真实样本上看到错误被解决的前后差异，比展示许多 Agent 名称更有说服力。

## 8. 必须主动放弃的诱惑

- 不把服务数量、GPU 档次、Agent 数量当作作品价值证明。
- 不为本赛题开发跑动轨迹复原、数字孪生或实时接入；不让动画遮住球和关键球员。
- 不把模型推断的选择结果写成官方命中率或胜率变化。
- 不在基础播放、证据对齐与新素材适应尚未稳定时投入完整反事实物理模拟。
- 不为争取随机第 24 个提交而推迟有效提交；问答与投篮共 10 分应另做人员准备，但不挤占关键交付值守。

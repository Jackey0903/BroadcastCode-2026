# BasketballSkills 研究核查与「关键一拍」适配判断

核查日期：2026-10-06。范围：通读论文正文及 A/B/C 附录，核查作者主页、公开仓库与模型/数据检索结果；没有运行外部项目代码、下载模型、部署服务或联系作者。以下明确区分论文报告、实际查到的公开产物与我们的设计建议。

**结论：优先借鉴其“先确认事件与人物，再取数据”的证据组织方式。当前不宜把完整 BasketballSkills 当作已可下载、可在本队 T4 上直接运行的产品依赖。** 我们的目标仍是输出准确、可核验的增强比赛成片，研究系统的问答成绩不能替代成片验收。

## 1. 原论文的紧凑事实索引

论文：[Towards Comprehensive Basketball Understanding，arXiv:2608.23435v1](https://arxiv.org/html/2608.23435v1)。作者为 Yirong Hu、Jiayuan Rao、Yu Zhang、Shangzhe Di、Weidi Xie；2026-08-24 预印本。

### 八项工具与依赖

|工具|论文实现|
|---|---|
|球员/球追踪|SAM 3 + 微调 RF-DETR + BoT-SORT|
|事件识别|PlayNet + 追踪结果|
|出手分区|PlayNet 六分类头 + 投手标识|
|球衣读取|Qwen3.5-9B；多帧裁剪|
|人脸识别|face_recognition + 头像库|
|知识检索|固定接口 + NBA_DB / SQLite|
|记分牌读取|Qwen3.5-9B|
|事件时刻定位|Qwen3.5-9B；已知事件|

### 四项组合技能

|技能|依赖顺序|
|---|---|
|Face-Conditioned Knowledge Retrieval|人脸 → 数据库|
|Shot Analysis|追踪 → 事件 → 分区或球衣|
|Identity-Grounded Play-by-Play Generation|追踪 → 事件 → 球衣 → 顺序事件表|
|Event-Conditioned Player Knowledge Retrieval|事件人物 → 球衣/球队 → 名单 → 知识|

控制器为 DeepSeek-V4-Flash；最多 12 轮、10 次工具调用。Verifier 检查调用合法性。BasketballBench：7,980 问、10 任务、2,501 片段。主要核对位置：§4、附录 B。

### 必须同时看的结果

- Q8 完整事件 F1：BasketballSkills **45.9**，GPT-5.4 **29.8**。
- Q7 时刻准确率：**47.8**，GPT-5.4 **77.5**。
- 加技能后，视频成绩 **72.76→72.34**；工具调用 **4.36→3.63**。
- Table 4 的 Target 使用真值框，非自动框。
- PBP 时间会滞后；数据筛除了时钟停顿等片段。

以上为作者报告而非本队复现；结果定义及限定见论文 Tables 2–5、Appendix A.3.2/C。论文把高级工具串起来，但精确时间和完整事件仍有明显误差；技能消融主要说明调用效率。

## 3. 对我们的比赛真正有价值的部分

以下均为结合本仓库规则、已看训练样片和现有方案作出的**工程判断**，不是论文已经证明的比赛效果。

### A. 把“是谁”放在“查他的数据”之前

我们最容易丢准确性分的错误，不是说错“这是一记投篮”，而是把正确数字贴给错误球员。为每次候选出手先建立 `event_id`，再绑定当前片段中的对象、球队、球衣号、本场名单记录，最后关联官方出手数据。没有完成前面的绑定就不显示个人指标。

建议保存独立字段：`candidate_actor_id`、`team_id`、`jersey_number`、`player_id`、`source_event_id`。临时视觉对象与真实球员 ID 不互相覆盖。这样能检查错误到底发生在“找错投手”“号码看错”“名单映射错”还是“官方事件匹配错”。

训练样片中，阿门片出现了其他球员的 PTS/FG/REBS 转播卡；这一结构可直接防止把卡上的数字当成当前投手的 xFG%。参见 [样片核查](公开训练样片核查.md)。

### B. 以具体事件为中心补看画面

让 Agent 输出“我需要确认这次出手的持球人和离手时刻”，再调用窄工具采集相应片段。不要让它在整段截图中反复生成完整篮球故事，重复调用不会自动带来新的事实。

可以保留同一候选人物的若干有质量的裁剪图，连同完整画面和时间标记供识别。跨镜头时建立新的片段对象；画面中断时不补造轨迹。球衣号和本场记录足以支撑我们的身份路线，人脸识别分支不纳入比赛方案。

这仍是短片中的局部证据采集与标签定位，遵守“不做跑动轨迹复原”的题目范围。论文使用追踪不构成我们扩张到完整轨迹系统的理由。

### C. 分开处理三条时间轴

为每条记录分别保存媒体时间、比赛节次/时钟、导出成片时间。官方 PBP 可用于限定候选窗口，但最终叠加的出手位置和时刻要由对应画面及官方点位核准。不能将游戏时钟直接相减当作视频秒数，也不能用比分刷新帧替代球离手帧。

建议先粗采样找到候选窗口，再局部加密检查；采样和裁剪必须保留原始 PTS。输出不能定位时，应保留区间或待核状态，不随便取中点再伪装成精确出手时间。若评测要求一个时刻，必须先明确事件定义并进行对应精度验证。

我们的两片存在近远景切换、记分牌布局不同和比分刷新延迟；因此固定左客右主、全片连续倒计时等假设不能直接搬进适配器。

### D. 技能成为可审查的操作规则

建议在现有 AgentCore 中实现少量清楚的程序技能，而非增加一大群只交换长文本的 Agent：

|我们建议的技能|输入与结束条件|关键产物|
|---|---|---|
|核对出手|候选出手窗口；找到对应投手、时刻、官方事件才完成|匹配记录与证据片段|
|核对人物|同一人物的画面、号码、本场名单；歧义未消除则保留未确认|身份绑定及证据|
|核对指标|官方数据、对象、事件与范围；全部一致才可发布|带来源和单位的指标记录|
|编排关键一拍|已核验事件；只选择有依据的 3–5 个解释节点|成片/网页共用展示清单|

这些是我们自己的产品实现建议，不是声称原论文已经有“篮球导演技能”。为技能设置预算、缓存、输入条件与退出条件，重点是减少无意义调用，确保中间对象没有被偷换。

### E. 调用合法与事实正确分别验收

我们可以很快做到 JSON 合法、文件存在和工具参数类型正确；这些不能保证说对篮球。建议把验收分为两层：

- 运行校验：接口、输入、路径、时间范围、唯一键、字段类型和重复调用。
- 内容校验：这个人是否确实实施了这次动作，数据是否对应同一次出手，标注是否出现在正确位置，解释是否超过了可见证据。

第二个模型可以找矛盾，但不能把“两个模型一致”升级为官方事实。两层检查各自留日志，方便出错时定位。

## 4. 不能直接照搬或夸大的地方

1. **问答成绩不是战术解释与成片质量。** 我们还要完成官方指标绑定、证据可点回、叙事选取、标注避让、烧录 MP4、CloudFront 播放与赛事统一接口。这些应作为自己的工程贡献与评测范围。
2. **完整事件表不是已核验的战术因果。** 找到传球者、投手和出手时刻，仍不足以证明某个动作“提升了多少命中率”或“迫使唯一防守选择”。指标从官方数据读，原因解释从画面和明确限制出发。
3. **真值框实验不承诺自动定位效果。** 它可以提示我们研究局部人物证据，但不能拿那一项提升作为我们产品的预期成绩或路演指标。
4. **技能效率不等于准确性提升。** 对本队最实用的主张是减少重复探索、固定依赖关系和支持恢复；准确率要在本队样片及新素材上测。
5. **上游错误会污染所有后续步骤。** 识别错投手后，即使名单与数据库每一步都工作正常，也会产出“看起来证据很齐全”的错误答案。证据卡必须指向真实画面，不能只展示工具调用成功。
6. **清晰样本的成绩不能保证困难镜头。** 我们必须主动覆盖遮挡、时钟停止、回放、球衣号不可读与多候选出手；测试中缺失/失败样本也计入分母。
7. **当前硬件适配未验证。** 本队 T4 CUDA 通路可用，不代表这些视觉组件可按论文环境同时运行、达到比赛时限。没有端到端运行证据前，不把论文结果当成本队延迟或显存保证。
8. **不复制论文中的完整事件范围。** 我们不做判罚认定；也不引入人脸识别、博彩预测或轨迹复原。只采纳与赛事交付相符的证据组织方法。

## 5. 可以立即落到开发验收的实验

使用已下载的两段公开训练视频建立一份小型人工核验表，明确这只是开发用样例，不能宣称具有大规模泛化能力。建议比较：

- A：整段直接问答；
- B：增加候选事件窗口和相关人物裁剪；
- C：在 B 上增加本场身份、官方事件与指标范围校验。

三组使用相同基础模型、相同输入资料和明确的调用预算，保存每次结果，避免把多看了官方答案或人工选框带来的优势算给 Agent。局部真值框可作诊断上界，必须与自动产生的框分开报告。

最少记录：投手关联是否正确、出手媒体时间误差、官方数据误匹配数、可发布解释中的无依据主张数、有效节点覆盖率、工具次数、总耗时。不要只报告“成功输出 JSON 的比例”；也不要通过隐藏所有不确定节点得到漂亮的准确率而不报告覆盖率。

开发先交付 **两个真实样片的正确增强成片**，再逐项替换感知模块。若后续获得可信 BasketballSkills 实现或权重，将其作为可比较的插件分支，不更改已经稳定的官方数据与渲染契约。

## 6. 研究定位与引用方式

在作品说明中明确引用这篇研究对领域工具、组合技能和事件人物绑定的启发；如果复用上游代码，再按具体仓库实际文件和许可记录，不把作者的成果改名为本队原创。

我们可主张的独立工作应由实际实现支持：针对赛事官方点位的数据适配、视频/比赛/成片时间映射、有限证据下的发布控制、不挡球的标注编排，以及让观众通过增强视频理解一次出手的交互体验。当前这些仍是推荐方案，尚未实现或测得提升。

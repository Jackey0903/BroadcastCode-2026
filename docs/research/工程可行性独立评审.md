# BroadcastCode 工程可行性独立评审

日期：2026-10-06。用途：为正式产品方案提供工程取舍，不构成新增赛事规则。本轮仅阅读资料和官方技术文档，没有部署、创建 GPU 或调用计费模型。

**本评审已按本轮新核准的[终极指南](https://csdn.feishu.cn/wiki/B3NSwj16GiSCR7kcM5vc9RjMnQb)和 [Quickstart](https://csdn.feishu.cn/docx/Y21TdJqrHopofmx2w21cmqHLnLb)调整**：必须 AgentCore、CDK 定义全部项目资源、CloudFront Web 交互和完整烧录成片；官方只提供出手瞬间点位，没有逐帧轨迹。统一接口和输入/产物路径以 Quickstart 为准，下面的内部 schema 由适配器转换，不能擅自替代官方契约。旧项目分析中的未确认事项须按新资料更新。

依据：[项目入口](../../README.md)、[AI 接手说明](../../AI接手说明.md)、[比赛分析](../archive/competition-2026/BroadcastCode-比赛规则与需求分析.md)、[部署约束](../archive/competition-2026/BroadcastCode-CDK与GPU部署约束.md)、[真实验证报告](../archive/competition-2026/AWS-Team02-服务实际验证报告.md)及 `aws-validation` 中的 JSON 证据。

## 1. 推荐的技术主线

**把一个进攻回合中 3–5 个有证据的关键决策解释准确，并让观众能在原画面上看见依据。** 数量是内部产品目标，应随素材长度和实际可识别事件调整。采用“镜头切分 → 稀疏帧理解 → 事件窗口加密 → 局部定位与标签锚定 → 数据核对 → 统一叙事时间轴 → 烧录成片与互动 Web”的流程。局部跟踪仅用于让标注跟住可见对象，不恢复、展示或推算球员跑动轨迹。官方边界明确不做实时、数字孪生、跑动轨迹复原、判罚与博彩。

最危险的方案是同时承诺全场球员身份、逐帧球轨迹、跨镜头重识别、完整场地三维重建和反事实战术胜率。它们会把短片比赛变成多个视觉研究课题，任何一个不稳都可能降低 55 分人工评审中的准确性和观感。

真正值得做成亮点的是：点一下“空位从哪来”，回到相应画面，依次显示持球威胁、协防移动、接应者获得空间。每一步有对应视频片段；已有官方指标时再展示准确匹配的数值。没有事件级数据时展示其真实统计范围，不生成伪造的即时概率。

## 2. 两种视觉路线的取舍

|方面|稀疏关键帧 + 事件内局部跟踪：推荐主线|全场轨迹复原：排除|
|---|---|---|
|目标|保证关键战术片段的标签位置和解读可信|给全部球员与球保持完整轨迹和身份；不作为本赛方案|
|镜头处理|每次切镜重置局部 track；回放单独标识|跨镜头重识别、回放重复事件去重更复杂|
|模型负担|先粗采样，再对 1–3 秒关键窗口加密|检测、跟踪、重识别、相机运动补偿长期运行|
|定位方式|预训练检测器候选 + 短时光流/跟踪 + 重检测；VLM 负责关联语义|必须持续解决遮挡、相似队服、球过小、出框再入框|
|失败表现|单个标注隐藏或收缩为关键帧解释，原视频继续播放|一次 ID 交换可能让后续全部标注和数据关联错误|
|对比赛价值|直接服务“这次进攻为什么成功/失败”的叙事|完整跑动轨迹复原超出新核准赛题边界，应排除|

VLM 返回的框只作为候选。仅有“红色图片识别成功”的测试，不能证明它在 NBA 转播中能稳定定位人、球或球衣号码。开赛前必须用真实 sample 比较两种白名单模型，不根据模型名预设优胜者。

实现细节：使用原始视频像素空间内的归一化坐标；定位球员可用脚部附近锚点画地面环，名称跟随身体上方。不能把框中心当作球场地面坐标，也不能在没有球场标定时输出真实距离或速度。切镜、长遮挡和离屏后停止轨迹插值；恢复时重新确认对象。传球箭头应有出球与接球的画面依据，不画未经观测的精确飞行轨迹。

## 3. 服务架构：优先复用已经打通的路径

```text
官方统一接口接收视频与数据（管理员/评委可触发）
    │
    ▼
S3 原始输入、素材摘要、输入哈希
    │
    ▼
Lambda：短片探测、切镜、抽帧、轻量 CPU 处理
    │
    ▼
AgentCore Runtime：调用工具、选择关键事件、补采样、核对数据
    ├── Bedrock Qwen3-VL / Claude：图像证据与篮球解读
    ├── 确定性校验：实体、时间、引用、指标范围、JSON schema
    └── DynamoDB：任务状态；S3：阶段产物与分析清单
    │
    ▼
同一份 analysis.json / timeline.json
    ├── 共享画面组件 + ffmpeg 烧录完整 MP4 → 指定 S3 产物路径
    └── React 交互页面、完整成片及证据章节 → CloudFront
```

Agent 需要实际做决策：观察证据不足时请求局部加密帧；调用数据检索工具匹配指标；丢弃没有证据的解释；将通过校验的事件交给确定性渲染器。多个角色可以是同一 Runtime 内的顺序步骤，无需建立多个独立 Agent 服务或自由对话的多智能体系统。

|组件/能力|本队证据|下一步验证|
|---|---|---|
|CDK、S3、CloudFront、Lambda、DynamoDB、日志|部署与基础读写实测通过，测试资源已删除|正式角色策略、媒体文件读取、缓存与页面访问|
|AgentCore Runtime 内调用 Claude|通过 CLI 发布与真实调用成功|改为 CDK 定义部署；异步任务、S3/DynamoDB 工具权限、超时/断线恢复|
|Claude、Qwen3-VL 图像接口|单张合成 PNG 调用通过|多帧输入、真实篮球识别、JSON 输出、账户限流和延迟|
|SageMaker `ml.g4dn.xlarge` Training|T4 CUDA 小矩阵运算通过|视觉模型兼容性、容器启动、数据下载、实际吞吐；用途须符合主办方许可|
|FFmpeg、视觉模型、视频导出|尚未做本项目端到端验证|Linux 打包、字体、编解码、内存、时间和最终效果|
|API Gateway / SQS / Step Functions / ECS / MediaConvert / Polly 等|当前报告未提供实际验证|若选用，应先验证权限和最小调用，不列入已完成能力|

以 Quickstart 统一接口、参数与输入/产物路径为外层契约，内部可以用状态机分阶段处理。必须在 AgentCore 内执行核心智能体流程，不能只有本机逻辑或模型调用循环。每队预置专属 S3 桶可导入使用，项目新增资源全部由 CDK 定义部署；不能用 CLI 创建正式 Runtime 替代 CDK。Web 必须提供可交互完整作品体验，不能交 Notebook、录屏或裸 API。完整考试成片与 CloudFront 入口应在 20:00–22:20 评审期持续可用。

已只读核对本地锁定版本 `aws-cdk-lib 2.272.0`：包含 `aws-bedrockagentcore.CfnRuntime`、`CfnRuntimeEndpoint` 和 L2 `Runtime`。L1 支持 `agentRuntimeArtifact.codeConfiguration`，字段为 `code.s3.{bucket,prefix,versionId?}`、`entryPoint`、`runtime`；另必填 `agentRuntimeName` 与 `roleArn`，可配置网络及协议。因此可将已测试的 Python ZIP 方案纳入 CDK，但 **CloudFormation 创建 Runtime 的实际权限仍需正式最小部署验证**。

不要为一个上传按钮在考试前引入完整用户账号系统。若开放上传，应采用服务器生成的 S3 上传地址、限制任务规模；浏览器不接触 AWS 密钥或模型凭证。

Lambda 的普通函数最长 15 分钟，媒体大文件应放 S3，调用只传对象引用；建议拆成可独立重试的小阶段，单阶段目标低于 5 分钟。FFmpeg/视觉依赖要提前为实际 Lambda 运行环境打包，不能把 macOS 本机二进制直接上传。[AWS Lambda 限制](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)

AgentCore 官方支持回应后继续异步处理，但本队历史示例只是同步 HTTP 服务。正式实现应按 SDK 异步任务机制维护运行状态，结果持久化到 S3/DynamoDB；不能仅启动后台线程就假定任务一定存活。[AgentCore 异步处理](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-long-run.html)

Converse 的通用约束包括单请求最多 20 张图、每图不超过 3.75 MB 和 8000×8000；具体模型支持和多图表现仍要实测。初始可按 8–12 张带准确时间戳的帧一批，分镜头送入，避免将整段视频逐帧送给模型。[Converse 接口](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-runtime/client/converse.html)

GPU 不在第一版可交付结果的必经路径。指南旧描述的 GPU 配额为 0，与用户随后转交的 SageMaker 开放通知及实际 T4 成功运行存在时序差异，应按后续通知和具体用途实测处理。SageMaker Processing 配额仍为 0，不能因 Training 成功而声称任意 Processing 作业获准；如果要将自定义视觉计算封装进 SageMaker 作业，先核准用途与实际部署路径。其排队、容器下载或容量不足不能阻止基础版产出。不承诺在 T4 上运行 235B 大模型；Qwen3-VL 的现有可用方式是 Bedrock 托管调用。

## 4. 先锁数据契约，再并行写界面与后端

建议核心 schema 至少表达下面信息。这是设计草案，不是已有官方数据格式：

```ts
type Analysis = {
  schemaVersion: string;
  runId: string;
  input: {
    videoSha256: string;
    officialMaterialId: string;
    width: number; height: number; durationMs: number;
  };
  shots: Array<{ id: string; startMs: number; endMs: number; replay: boolean | null }>;
  entities: Array<{
    id: string; teamId: string | null; playerId: string | null;
    displayName: string; identityEvidenceIds: string[];
  }>;
  events: Array<{
    id: string; shotId: string; startMs: number; endMs: number;
    title: string; observation: string; interpretation: string | null;
    evidenceIds: string[]; metricIds: string[]; annotationIds: string[];
    status: "supported" | "uncertain" | "rejected";
  }>;
  evidence: Array<{
    id: string; kind: "frame" | "official_record";
    sourceRef: string; sourceTimeMs?: number;
  }>;
  metrics: Array<{
    id: string; officialName: string; value: number; unit: string;
    scope: "event" | "game" | "season" | "other";
    entityId: string | null; sourceRecordId: string;
  }>;
  annotations: Array<{
    id: string; shotId: string; entityId?: string;
    startMs: number; endMs: number;
    kind: "ring" | "arrow" | "spotlight" | "label";
    anchors: Array<{ sourceTimeMs: number; x: number; y: number }>;
    gaps: Array<{ startMs: number; endMs: number }>;
  }>;
};
```

时间以解码后原视频 PTS 映射的毫秒为依据；不要假定所有素材恒定帧率。比分牌比赛时钟、视频播放时间和事件数据时间是三个不同概念。若有慢放、回放或暂停，建立显式对应关系，缺少映射时不把官方事件数据硬贴到视频上。

官方点位仅对应出手瞬间。适配器必须明确其坐标系（画面像素、归一化画面或场地坐标）和时间，未核准映射前不能直接当作视频坐标。不得对这些瞬时点位线性插值成整段跑动轨迹。

姓名不确定时允许“右侧底角接应者”，内部保留匿名实体 ID。指标数值只从数据适配器读取，模型不能自由填写。解释中的事实与推断分字段存储；不要展示未经校准的“AI 置信度 97%”。界面可以告诉观众“画面证据”或“战术解读”，而非把内部调试信息堆在视频上。

缓存键包含视频哈希、数据版本、提示词版本、模型 ID 和阶段版本。状态机至少有 `queued / processing / partial / ready / failed`。每个阶段保存结果，重试不重复全流程；同一次运行的产物使用独立目录，发布时再更新小型 manifest，避免评委加载到半成品。

## 5. 播放器与导出必须共享时间轴

推荐定义纯函数式 `OverlayScene(analysis, sourceTimeMs, viewport)`，统一生成圈、箭头、遮罩、字幕和数字卡。互动网页和导出均消费同一份结构化结果与布局规则。Remotion 是可评估的实现候选，其 React 组件支持时间驱动渲染和参数化播放器；这不意味着 Remotion 的 AWS 渲染链路在比赛账号上已经验证。[Remotion 基础](https://www.remotion.dev/docs/the-fundamentals)、[参数化与播放器](https://www.remotion.dev/docs/parameterized-rendering)

**完整烧录成片是 P0，浏览器叠加仅作为交互增强，不能替代成片。** 用同一 scene/schema 生成逐帧透明图层或合成画面，经 ffmpeg 编码成带名字、指标、箭头的完整 MP4。首版保持原视频时长和节奏。若加“关键时刻停顿解读”，使用独立的 `presentationTime → sourceTime` 编辑映射；视频、字幕、标注、语音全部使用同一映射，不能只暂停其中一层。导出测试至少检查开头、中间、结尾和每次切镜的位置，不以网页看起来正确推导 MP4 一定正确。

浏览器尺寸变化时基于视频实际内容区域计算 letterbox 偏移，不能把归一化坐标直接乘整个容器尺寸。播放、拖动、倍速和章节跳转都以当前媒体时间重算标注。失去可靠跟踪的区间隐藏动态锚点，可保留时间对应的文字解读，不能持续漂移。

媒体使用带版本的 URL 和内容哈希；最终 manifest 短缓存，素材长缓存。考试阶段优先更新数据与媒体，避免因一次文本修订重建整个 CloudFront 分发。

## 6. 时间与成本预算

下面都是内部目标，**尚未在真实素材上达到或测量**。以 30–60 秒短片为第一次基准；考试素材若更长，必须按长度重新评估，不能宣称固定时间完成。

|阶段|初始设计预算|超出时的动作|
|---|---:|---|
|输入检查、上传、切镜、粗抽帧|3–5 分钟|降低工作副本分辨率，保留原片|
|粗理解与关键窗口加密|5–8 分钟|限制候选事件、降低并发重试、保留通过校验的部分结果|
|事件、身份、指标核对|3–5 分钟|身份匿名化，缺字段不编造|
|局部视觉增强|5–10 分钟|只保留可靠窗口和关键帧标注|
|第一版可交互结果发布|目标 20 分钟内|尽早发布 partial 结果供检查|
|带标注视频导出、上传与外网检查|再留 10–15 分钟|预先验证低分辨率完整导出；不能降级成只有网页叠加|
|一次完整处理、检查与发布|目标 45 分钟内|考试还保留一次有范围的修正和重新发布机会|

建议先粗采样约 1 fps，再对少量关键窗口增加帧密度。单条短片第一版可设 8–12 次多模态调用的硬预算，默认并发 2，按实际限流调整；禁止无上限“反思直到满意”。这是成本和时延控制起点，不是认为任意篮球事件都能由这个固定预算正确识别。

先测真实吞吐，再决定是否引入 GPU。GPU 实测 199 秒只对应一个极小 CUDA 检查，不能拿来估计检测模型、转码、视频导出或冷启动任务总耗时。

## 8. 最可能拖垮考试窗口的风险

1. **直到 18:00 才知道数据字段和时钟映射。** 现在拿到 sample 就做适配器，未知字段保留原始记录；没有同粒度数据就显示范围，不硬拼。
2. **把云 GPU 当成实时可获得资源。** 不让新 GPU 容器下载/启动成为首版结果依赖；所有 GPU 增强都应可超时退出。
3. **依赖每个球员都能识别姓名。** 以局部实体和球衣颜色/位置建立叙事，只有身份依据充分时显示姓名及个人指标。
4. **采样过稀却断言精细动作。** 粗扫描后主动补采样，无法补足证据则降低解释粒度；不把一帧姿态写成完整战术因果。
5. **网页叠加正确但导出完全另一套逻辑。** 共用 scene/schema/time mapping，从第一天就导出短片测同步。
6. **引入未经验证的服务抢技术分。** 新指南明确机器评审关注架构稳定性、AWS 有效使用、服务组合协同性与完整输入处理输出链；每项服务必须服务真实能力，不按数量赌博。
7. **匿名网页直接调用模型或持有 AWS 凭证。** 后端代理和最小可运行访问路径尽早定好；第一版评委浏览不依赖重新登录 AWS。
8. **考试阶段做基础设施迁移。** 18:00 前已有稳定 URL；最后两小时原则上更新素材、分析与版本清单。
9. **连续重试改写已经正确的部分。** 保存阶段缓存和失败原因，限制尝试次数；可以发布带明确范围的部分完成结果。
10. **把人工画线伪装成自动能力。** 正式素材从文件输入生成结构化输出；如规则允许修正，保留原始自动结果和修订记录。

## 9. 开发前最有价值的验收关卡

先做一段训练视频的真实端到端样机，交付：输入哈希、符合 Quickstart 的调用与产物、CDK 部署的 AgentCore、3 个有证据的事件、至少一个可靠动态标注区间、一项准确引用的官方指标（仅在确有对应数据时）、CloudFront 可互动网页、同时间轴完整烧录视频和一次处理耗时记录。

然后用另一段尚未用于调试的样例替换输入，保持流程自动运行；尽量避免看到第二段素材后为它加入固定时间点或球员答案。开发前的“冲第一名方案”只有在这道验收关卡后，才可以转化为可信的交付承诺。

## 10. 用一个可测的小算法支撑“实现深度”与视觉效果

新指南决赛权重为架构 18、实现深度 18、准确性 15、讲解 9、视觉效果 40；只有一轮 5 分钟讲解加提问，初赛分数不带入。实现深度可以来自算法和识别结果二次加工，不需要夸大成新的篮球预测模型。推荐实现 **带证据门控的稳定标注布局算法**：它直接改善名字和指标标签对真实转播画面的遮挡与抖动，并可用对照视频证明效果。

1. 输入来自真实证据的可见锚点、人物保护框、比分牌区域、当前镜头边界及已激活事件。某个锚点失去证据时停用，不推演其隐藏运动；出手瞬间的官方点位只在已对齐的对应时刻使用。
2. 每个标签枚举上下左右及对角等 8 个候选位置，同时给出“暂不显示”选项。出框、覆盖比分牌或遮住主要持球对象的候选可先排除。
3. 在最多 3 个关键标签的画面中，枚举最多 `9^3 = 729` 个组合，最小化统一代价：`J = w1×人物遮挡 + w2×标签重叠 + w3×锚点连线长度 + w4×相邻帧位移 + w5×暂隐惩罚`。这是有限候选搜索，容易调试和复现。
4. 使用位置切换滞后规则：新布局只有在收益超过阈值并保持若干帧时才替换旧布局；切镜立即重置。所有超参数在训练素材上固定，考试时同样自动运行。
5. 权重与门控阈值是工程参数，不能称为官方篮球指标。输出供渲染器使用的布局状态，不输出速度、跑动距离或重建轨迹。

验收报告用相同视频、相同文本和相同锚点，对比“固定上方标签”“只有避让”“避让加稳定约束”三版，记录：标签互相重叠的帧比例、遮住人物/比分牌的帧比例、每秒标签位置切换次数、标签有效显示时长和平均每帧布局耗时。人工检查片段确保降低遮挡没有靠把所有标签全部隐藏完成。展示原始指标和对照画面，不预先承诺改善百分比。

这一个算法同时回应实现深度和 40 分视觉效果，复杂度小，能在浏览器预览和烧录导出复用。相比额外拼接一个未经验证的大模型，它更容易在 5 分钟决赛里讲清“问题、方法、对照、收益”。

### 1\.1 赛题与交付物

- **赛题**：交付一个能对比赛画面做**视频理解 \+ 数据可视化 \+ 现场解读**的 Agent —— 选手相当于"化身为解说员"，把视频交给 Agent，由 Agent 理解并解读比赛画面。

- **输入**：主办方提供两段比赛训练视频 \+ 一段考试视频。视频输入 Agent 后，需输出一段把数据可视化、战术跑位等画面**叠加到视频上**的成片，也可以把解说加入视频之中。

- **对标产品**：2025 年 NBA 总决赛期间，腾讯 NBA 直播中的「NBA 深度赛场」解说即同类产品——当时是基于亚马逊云科技的光学追踪引擎与大模型技术实现的赛场理解。选手可以找当时的直播回放参考。

- **交付物形态（主办方举例，非强制、非限制）**：

    - 实时标注球员位置，让不懂篮球或第一次看球的观众也能一眼看懂画面在表达什么；

    - 标注战术意图，解释"这次关键选择为什么没有投篮而选择了助攻"；

    - 标注球员行为动因——为什么做这次传球、为什么做这次投篮；

    - 标注投篮难度，以及这次选择与平时选择有何不同；

- **明确不设限**：以上只是"想象力的起点"，未写在要求里的东西做出来了，代表理解更出众。鼓励更随心所欲地解读赛场。

## 二、议题二：「深度赛场」数据解读

> 主讲：王乐（NBA 中国高级产品经理，负责 NBA 官网与 NBA APP）｜01:21:08–01:28:59

### 2\.1 数据来源

- 数据采集于**上个赛季常规赛期间**，由部署在 NBA 现场的**鹰眼相机**采集。

- 经 AWS 技术分析（转写中作"阿里云的 IOS 技术"，**待核**），主要分析球员身上的 **29 个关键点**。

- 结合 AWS 模型，产出普通数据（投篮、得分、篮板、助攻）之外、但对比赛影响力更大的新概念数据。

### 2\.2 三大核心数据

本次希望选手在视频可视化中重点呈现这三项：

**（1）预期命中率**

- 含义：在一次投篮事件发生时，通过现场人体模型采集，为球员分析出的预期命中率。

- 影响因素：球员自身的投篮姿势、起跳高度、出手角度；以及周围防守人施加的防守压力。

- 官网呈现：NBA 中国官网设有「深度赛场」专题。以今年总决赛马刺对尼克斯的一场为例，图表从左到右为预期命中率由低到高分布；纵向越集中，代表该位置上出手的数据量越大（示例中尼克斯主要集中在该值 50 以下的区间）。

**（2）球员引力（Gravity）**

- 含义：球员在持球与非持球过程中，对场上其他防守队员的吸引程度。

- 值越高，代表在场受到的防守关注度越高；值越低，则容易被放空。

- 细分为**持球引力**与**无球引力**，反映拿球前后引力的变化幅度。

**（3）胜负影响率**

- 含义：综合衡量球员场上所有行为对比赛胜负的影响值。

- **不只看得分**：投中关键球影响很大，但关键抢断、关键防守造成对方失误，并在下一回合转化为己方得分，同样会显著拉高该值。

### 2\.3 数据获取与使用原则

- 除三大核心数据外，中国官网与美国官网还有大量**基础数据**（得分、篮板、助攻）与**进阶数据**（真实命中率、进攻篮板率、防守篮板率等）。

- 比赛系统 Portal 中提供了中国官网与美国官网链接，可直接跳转查看；对数据项有疑问，官网数据说明可解释其基础含义。

- **使用目的有两点**：一是让比赛视频更炫酷——常规只放精彩进球，观众难以理解这个球的意义；二是让数据被用户更好地理解。举例：倒地绝杀的投篮预期命中率一定很低，若投进，就是一个预期命中率极低的精彩球，数据可以把"精彩"具体量化呈现出来。

- **重要提醒**：不希望选手只是把数据简单堆叠在视频上——一大堆数据会影响整体呈现，出现**喧宾夺主**的情况。用哪些数据、如何呈现、如何与视频结合解读，正是本次黑客松留给选手的题目。

## 三、议题三：比赛系统、云资源与自动评分规则

> 主讲：郭晓东（AWS 解决方案架构师，本次比赛技术支持方）｜01:29:24–02:00:29

### 3\.1 比赛系统（Portal）：一站式入口

- **登录**：链接与用户名密码由主办方在合适时间发放。用户名有规律——队伍编号为 t05 则用户名为 t05；密码各队不同。忘记密码可联系组委会 reset。

- **核心功能**：

    1. **提交 GitHub repo**（必需，且必须为私有仓库）；

    2. 下载比赛必需数据（也可在此外自行获取更多数据，不限制）；

    3. 一键跳转至分配给本队的 **AWS 云资源账号**控制台；

    4. 提供 **AWS CLI 详细用法说明**，便于用 AI 来操作云资源；

    5. 提供**范例代码（sample）**，拉低学习成本；

    6. 一键打开**参赛指南**与 **Quick Start**（于明浩以参赛者视角撰写的快速操作指南）；

    7. **提交最终作品 URL**。

### 3\.2 GitHub 仓库绑定（关键步骤）

- 登录 Team Portal 后**第一件重要的事**：report（绑定）你的 GitHub repo。

- **仓库必须为 private**。若为 public：① 成果可能被扩散，影响比赛结果；② 系统后台会标记为不合规，工作人员会联系要求改为 private；**若一直不改，将失去 35% 的自动评分**。

- **绑定流程**：点击 connect GitHub repo → 弹出 GitHub Agent/App 授权窗口 → select repositories → install → 输入本人 GitHub 密码（通过 OAuth 交换密钥，主办方刻意如此设计以保护选手安全）→ 将该 repo 的**只读（read）权限**授予比赛系统。完成后不可自行更改；若不小心选错，联系组委会在后台 reset 后按钮会重新出现，可重选。

- **提交有效性**：以 **10月10日 20:00 前 repo 中最后一次 commit** 为有效提交，超过该时间的任何提交都被忽略。
**强烈建议随时提交**——完成一个小功能就 push 一次，不要等到最后时刻。

### 3\.3 AWS 云资源账号

- 每个**参赛队**（不是每个人）分配一个 AWS 账号（形如 12 位账号编号）。

- 选手需在账号内完成比赛、部署出最终的 Agent，并产出一个观感良好的页面。

- **跳转方式**：Portal 内两步操作（点击 → 等待完成 → switch to your account）即可进入本队账号，背后涉及 AWS IAM 权限交换，主办方已把难度降到最低。

- **区域限制**：**只允许使用指定区域的资源**（转写中作"美中一 / 每周一"，区域码 us\-east\-1 待核）；使用其他区域会被限制，控制台出现大量红叉，用 AI 操作其他区域也会报错。

- **创建资源的方式**：不建议在控制台手工点击创建（太慢，不适合比赛）；正确做法是走 **AWS CLI**——Portal 提供了完整操作步骤，甚至可以把这段步骤直接交给 AI 或 Agent 工具，由它帮你配置。拿到权限后即可用自然语言 \+ MCP 的方式让 AI 快速搭建系统。

### 3\.4 数据与参考资料

- Portal 内可直接跳转到 NBA 深度赛场数据与 NBA 官方数据地址，无需单独记忆。

- 参赛指南（于明浩撰写）与 Quick Start 均可一键打开，第一遍直播没听仔细的同学建议事后补读。

- **sample 代码**：AWS 架构师团队专门编写了示例，包括模型 ID 在 Amazon Bedrock（转写中作"my log / bat rock"）中该如何书写、平台该如何调用等。没有基础的同学建议赛前阅读，事半功倍。

### 3\.5 评分规则（自动评分部分）

**三个"必须"**

1. **最终发布为 CloudFront URL**。只认可 CloudFront URL，不接受随手给的 IP 地址或 ALB 地址；评委在 20:00 完赛后直接打开该 URL，从**美感、操作性、准确度**三方面查看交互式页面并评分。不清楚什么是 CloudFront URL，可以向 AI 询问。

2. **使用 AWS CDK 发布应用**。CDK 是 IaC（基础设施即代码）的一种实现手段，可一键部署——一个 CDK 工程运行完，即可把所需 AWS 资源一次性部署到分配好的账号中。

3. **AI Agent 必须部署到 AWS 的 Agent 服务**（转写原文即"AWS 的 agent 服务"，**具体服务名待核**）。

**三项均为硬性要求，每一项都占大量分值**：第 3 项缺失几乎等于放弃比赛，第 1、2 项缺失也会丢掉大量分数。

**自动评分原则**：鼓励**多样化使用 AWS 托管服务**，而不是自己拿一台虚拟机装开源软件搭一整套系统——后者无法体现对 AWS 服务的熟练程度，也体现不出托管服务的多样性。托管服务用得越多越多样，这部分分数自然越高。

### 3\.6 资源限制与模型服务

- **区域限制**：见 3\.3。

- **模型 API**：主办方提供两个模型——一个转写作"夸我们 4\.6"（**型号待核**），另一个为**千问 235B**。

- **不限制使用外部 API**：选手可自行使用已有 API（如自有平台或第三方 API）。但外部 API 涉及密钥问题，务必用稳妥方式保管，**不要 push 到 GitHub、不要遗留在环境中**。

- **全真模拟环境**：考虑到 AWS 使用难度较大、门槛较高，主办方将在**国庆假期后半期提供 2–3 天全真模拟**，环境与比赛完全一致（含 Portal），供选手提前熟悉、调试，尽量把问题留在赛前。

- **AI 工具**：鼓励且不限制使用各类 AI 编程工具。

### 3\.7 比赛纪律

- **严禁任何形式的作弊行为**，包括但不限于串通、抄袭，或影响他人。

- **严禁任何影响比赛系统正常运转的行为**——例如好奇去嗅探系统、扒 API，甚至尝试篡改比分。主办方配有安全团队，一旦查实，最严重处罚为**直接取消比赛资格**，绝不开玩笑（目的是保护所有选手的利益）。

- **禁止滥用分配的账号**：如疯狂调用 API 产生不应产生的费用，主办方保留处罚权利，违规产生的费用由违规参赛者自行承担。

- 分配到 AWS 账号后，**不得进行与比赛无关的操作**。

## 1. 赛题与硬性技术要求

输入 NBA 深度赛场数据和真实比赛视频，Agent 输出带数据可视化的比赛画面，并通过交互网页呈现。

- **必须使用 Amazon Bedrock AgentCore 承载智能体能力**。只在本地运行逻辑或仅做一个模型调用循环不满足要求。
- **必须通过 CloudFront 发布，且具备 Web 交互界面**。命令行、Notebook、纯 API、单独录屏都不能替代。
- **基础设施必须用 AWS CDK 定义和部署**。只用 CLI、控制台、Terraform、SAM 或裸 CloudFormation 不构成替代。
- 全部应用资源在赛事分配账号的 `us-east-1`。
- 数据必须叠加进真实比赛画面，球员名称、位置和对应指标应准确；解说是可选项，可以由 AI 或人工产生。使用 AI 解说时应明确声明。

Quick Start 的建议流程是 S3 输入 → AgentCore → Bedrock 理解 → ffmpeg 将名字、指标、箭头等烧录到视频 → CloudFront 发布完整成品及 Web。它明确要求成品视频，因此方案将**可播放的增强 MP4**作为 P0，浏览器交互作为配套，不能只依赖页面临时叠加。

## 2. 输入数据与赛题边界

- 官方深度数据**只有出手瞬间点位，没有逐帧轨迹**。仍需取得实际字段、坐标系、单位、时间映射和样例。
- 排除实时信号接入、数字孪生、跑动轨迹复原、判罚认定和博彩预测。
- 早上抽签分配白天调试的练习视频；最终考试视频于 18:00 发布。不要把练习分配和最终考试素材混为一谈，具体文件以现场发放为准。
- 可补充 NBA 官网数据及合法训练素材；交付物不能包含未授权录像，来源需要披露。

工程解释：短时间的画面标签定位与官方出手快照可支持展示；不要把它包装成连续球场轨迹重建。叙事和指标必须以样例中的实际信息为依据。

## 3. 初赛评分与排序

|项目|分数|核准内容|
|---|---:|---|
|机器评分|35|架构与稳定性、AWS 服务有效使用、服务协同、输入到输出链路完整；从代码仓库重跑|
|数据／内容准确性|30|NBA 侧评委核对内容与比赛事实|
|UX／UI 与作品体验|25|AWS SA／技术侧评委体验作品|
|球迷知识问答|4|3 题，答对 2 题满分；答对 1 题得 2 分|
|24 秒投篮|6|累计 6 分满分，要求罚球区外出手|

机器分鼓励托管、无服务器、事件驱动与 IaC；同一服务的实际使用深度会影响技术评价。没有取得 35 分内部的精确分配公式，因此不能按服务数量虚构加分。

并列时依次比较：人工分 → 机器分 → 内容准确性 → UX/UI → 问答。

## 4. 决赛形式与权重

初赛前八晋级，**初赛成绩不带入决赛**。决赛只有一轮，全体约十名评委评价同一场路演，不再分技术轮与内容轮。指南日程写每队 5 分钟讲解并有现场评分、提问；答辩另占多少时间需服从现场安排。

|决赛项|权重|主要评价内容|
|---|---:|---|
|技术方案与架构|18|架构说明、完整链路、AWS 选型与分工|
|实现深度与难度|18|算法、统计、识别后二次加工等实际工作，超越简单调用与展示|
|数据运用准确性|15|球员姓名、号码、球队、指标和画面对应|
|讲解与答辩|9|条理、时间和回答问题的质量|
|视觉与作品效果|40|可视化、篮球叙事、感染力、质感、交互及创新|

评委各项按 1–10 打分，再按上述权重折算。冲冠方案应把视觉叙事作为最强记忆点，同时用可复核的数据加工和工程链路支撑 36 分技术项。

## 5. 提交与评审窗口

- 北京时间 2026-10-10 **20:00 硬截止**；指南为考试视频留出 18:00–19:45 调优、19:45–20:00 提交。
- 提交包括部署的 Agent、私有 GitHub 仓库、说明文档、演示视频、承载完整考试作品成片的 CloudFront 公网链接。
- CloudFront 链接至少覆盖 **20:00–22:20** 审核时段；为决赛和后续安排保留多久还需按主办方通知处理。
- Portal 可多次提交 URL，后一次覆盖前一次，两次间隔至少 1 分钟；截止前最后一次提交为最终链接。
- 官方文档描述仓库绑定后锁定，组委会从绑定仓库拉代码；不能任意换仓库。本队绑定状态仍需依据自己的 Portal 核对，本次没有创建或绑定仓库。
- 机器评测存在统一 Agent 接口、输入参数、产物路径的要求，但本轮已读取的 Quick Start 章节没有提供可直接实现的完整 schema。必须拿到具体样例再适配，不能假装自定义内部格式就是官方协议。

# GameBuddy 三页技术答辩讲稿

## 第1页：整体技术架构（约40秒）

GameBuddy采用数据证据驱动的多模型架构。左侧把真实比赛视频与基础、高阶派生和深度赛场数据统一关联。上方的3B数据球探学习调用工具和选择证据，AgentCore上的多模态Agent结合真实帧与这些证据组织回合解读。程序负责校验统计口径、复制可信数值，并通过FFmpeg生成永久烧录的完整MP4。底部AWS流水线承担异步处理、状态管理和独立验收，最终通过S3与CloudFront交给观众。

讲解抓住分工：数据球探选证据，视觉Agent解释画面，确定性程序保证显示事实与视频交付。

范围：整体能力图包含两条分别验收的路径。自动RL样片实际调用训练后的3B并进入Agent叙事和烧录；正式55秒作品采用编辑视觉和AgentCore稿件审核。图中的战术注释为编辑示意。

## 第2页：Agentic RL与三层数据融合（约50秒）

我们把基础数据、高阶派生数据和深度赛场数据组织为一套多维度篮球证据模型，统一球员、比赛、事件、单位、统计范围与来源。它既生成模型的训练任务，也支撑Agent取证和最终展示。

我们以Qwen2.5-3B为数据球探，先做QLoRA监督微调，再进行Agentic RL，让模型在工具环境里选择查询、证据ID和受控关系。模型选证据，程序依据原始记录取得数字，并进行语义核验及有限纠错。这样形成可追溯的解读。

产品实测中，两段注册样片的三种关注方向共6个组合最终通过，其中5次直接通过、1次纠错后通过。弗拉格任务一次真实取证耗时2.841秒，三层证据进入Agent叙事并烧录到完整MP4。

口径：这里展示训练设计和系统落地效果。6/6是已知素材上的模型与程序护栏组合验收，2.841秒为一次任务的取证耗时。未把这些值当作RL相对SFT增益或新比赛泛化准确率。高阶指标为确定性派生，赛季引力为背景，单次xFG另外保存。

## 第3页：AWS服务协同与工程规范（约50秒）

我们用AWS把模型能力组织为真实生成和交付链路。AgentCore和Bedrock承担Agent托管及多模态推理，SageMaker承担数据球探训练和端点服务。Lambda与SQS处理长任务，DynamoDB保存阶段和预算。S3保存证据与完整成片，CloudFront向观众提供网页和媒体。成片持久化后，EventBridge触发Step Functions独立验收。CloudWatch记录运行状态并配置6项失败或积压告警。Polly与Rekognition提供可选语音和场景辅助能力。

规范体现为具体做法：CDK与CloudFormation管理主链基础设施，IAM工作负载角色遵循赛事权限边界，部署前用STS核验身份；私有S3通过CloudFront OAC交付；队列具备重试和死信机制，Worker单并发控制资源与推理预算；生成完成与交付验收分别保存，可选派生失败保留主成片。

统计口径：13项业务能力，AgentCore与Bedrock分计。CDK为工具，CloudFormation、IAM、STS作为工程支撑另列。Polly和Rekognition为已实测可选辅助，并不意味着正式55秒作品逐一调用所有服务。正式双人TTS使用外部服务。SageMaker训练与端点另有SDK脚本。以上描述比赛期间的实际实现，不宣称外部AWS认证。
